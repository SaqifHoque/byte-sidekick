# Feature delivery plan

Each numbered item is one feature-specific PR with at least five small, meaningful commits. Keep commits reviewable; do not squash away the requested history. A phase is complete only when its product-brief acceptance criteria pass. PR 1 is the shell foundation, not a claim that Phase 1 is complete.

## Phase 1 — Working desktop companion
1. Secure runnable desktop shell: build tools; isolated native window; typed IPC; Japanese React shell; CI and launch verification.
2. Animated vector Byte: asset contract; expressions; transitions; intensity; reduced motion and verification.
3. Desktop controls: transparent avatar; dragging and bounds; tray; help shortcut; hide/show and recovery.
4. Local settings and onboarding: schema; storage; language; permission defaults; restart verification.
5. Real configurable local model adapter: capabilities; loopback transport; timeout/cancellation; provider settings; error and live integration checks.
6. Grounded Japanese chat: orchestration; pasted context review; streaming UI; explicit copy; missing-fact and injection evaluation.
7. SQLite confirmed memory: schema; repository; save/retrieve; edit/delete/export; restart and isolation verification.
8. Phase 1 completion: focus/mute; standard-window accessibility; offline demo labeling; end-to-end checks; capability documentation.

## Phase 2 — Voice and requested awareness
9. Push-to-talk: explicit activation; permission; recording state; cancel; text fallback.
10. Speech output: provider contract; playback queue; stop; amplitude animation; mute checks.
11. On-demand window capture: selection; permissions; exclusions; context review; transient cleanup.
12. Approved document import: scope; parsing; full-text retrieval; provenance; revocation.

## Phase 3 — Development context
13. Repository reader: approved roots; exclusions; path containment; provenance; adversarial tests.
14. Diff review: import; structured changes; grounding; Japanese explanations; evaluation.
15. Editor adapter: authenticated local input; selected code; test events; deduplication; integration checks.
16. Checkpoints: records; save; restore; project isolation; restart verification.
17. Requirement checks and Japanese reports: criteria extraction; contradictions; PR draft; progress report; fixtures.
18. Failed-test suggestions: evidence; trigger policy; deduplication; focus suppression; acceptance checks.

## Phase 4 — Communication and proactive support
19. Connector foundation: scopes; identity; authorization; token storage; revocation tests.
20. GitLab read adapter: authentication; tickets; merge requests; sync resilience; isolation tests.
21. Slack read adapter: scopes; thread retrieval; grounding; expiry; revocation checks.
22. One configured mail provider: selection; supported auth; thread retrieval; draft review; failure tests.
23. Calendar retrieval: auth; events; timezone handling; availability; disconnect checks.
24. Confirmed commitments: proposals; owner/date review; persistence; due signals; ambiguity tests.
25. Meeting briefings: source selection; decisions; open questions; follow-through; evidence evaluation.
26. Proactive policy: quiet hours; cooldown; daily budget; snooze; deterministic policy tests.
27. Exact action review: proposal contract; destination review; authorization binding; audit; rejection tests.

## Phase 5 — Distribution and broader workflows
28. Windows packaging: configuration; unsigned build; install check; uninstall; documented platform results.
29. macOS packaging: configuration; unsigned build; signing hooks; notarization hooks; verified limitations.
30. Updates: threat model; signed feed; review controls; recovery; platform verification.
31. Privacy/data lifecycle: retention; export; delete; derived-cache cleanup; audit tests.
32. Resource baseline: measurement harness; idle; inference; capture; published hardware-specific results.
33. Broader workflow templates: release readiness; impact; handoffs; glossary; grounded evaluation.

Signing, notarization, external accounts, and real-provider acceptance require available credentials/services. Windows testing requires Windows. Record unavailable checks honestly; fixtures never count as live acceptance.
